## Структура проекта и назначение файлов

* **`Session.kt`** - ядро модели данных и правила доменной валидации
* **`Parser.kt`** - построчный парсер с пошаговой валидацией приоритетов
* **`ParseError.kt`** - sealed-иерархия причин отказов и строгий форматтер вывода
* **`Repository.kt`** - слой изолированного хранения данных и журналирования (аудита)
* **`Commands.kt`** — реализация логики верхнеуровневых команд (`runPeriod`, `runType`, `runErrors`). Запускает потоковую обработку файлов, фильтрацию занятий и выводит итоговую статистику в консоль

## Сборка:

### Выполните компиляцию, прогон Unit-тестов и создание нативных скриптов запуска:

**Windows PowerShell:**
```powershell
.\gradlew.bat build :app:installDist
```

**Linux / macOS:**
```bash
bash ./gradlew build :app:installDist
```
### После сборки исполняемые скрипты находятся в `app/build/install/schedule/bin/`.
### Примеры команд:

* **Выборка занятий за период (`period`):**
  ```bash
  ./app/build/install/schedule/bin/schedule period --file samples/clean.txt --from 2026-09-28 --to 2027-05-13
  ```
* **Фильтрация по типу занятия (`type`):**
  ```bash
  ./app/build/install/schedule/bin/schedule type --file samples/dirty.txt --type EXAM
  ```
* **Вывод агрегированного списка ошибок (`errors`):**
  ```bash
  ./app/build/install/schedule/bin/schedule errors --file samples/dirty.txt
  ```

### Генерация большого файла и запуск всех тестов из скрипта (включая мои кастомные)
```bash
python tools/generate_samples.py --huge
python tools/verify.py --huge --custom
```

## Обоснование архитектурных решений:
### 1. Выбор между `class` и `data class` для доменной модели

**Обоснование:**


### 1. Выбор между `class` и `data class` для доменной модели
Изначально для сущностей расписания рассматривалось использование `data class`
Однако для обеспечения абсолютной инвариантности выбор был сделан в пользу **обычных классов (`class`) с `private constructor` и фабричным методом `invoke` на `companion object`**.

**Обоснование:**
* **Защита от обхода проверок через `.copy()`:** Спецификация `data class` автоматически генерирует публичный метод `.copy()` 
Он позволяет скопировать объект, подменив любое свойство в обход логики инициализации
Использование стандартных классов полностью закрывает эту уязвимость
* **Оптимизация выделения памяти:** При использовании классического конструктора со встроенным блоком `init`, валидация данных запускается после того, как JVM выделила память под экземпляр
С `Companion.invoke(...)` выполняет все базовые структурные и доменные проверки (контрольные символы, внешние пробелы, корректность полей) до создания объекта
Если данные некорректны, исключение выбрасывается сразу, не выделяя память на сырой объект

---
### 2. Защита коллекций от внешних изменений
Модель гарантирует неизменяемость коллекций преподавателей:
* Изменяемый список, переданный в фабричный метод, не сохраняется как прямая ссылка
Вместо этого создается его неизменяемый снимок через `java.util.List.copyOf(teachersRaw)`.
Любые последующие манипуляции с оригинальным списком вне объекта (например, `.clear()` или `.add()`) не влияют на внутреннее состояние сессии
* При попытке принудительного приведения типа к `MutableList` и вызове мутирующих команд (`.clear()`, `add()`), будет выброшена `UnsupportedOperationException`.


### 3. Поведение делегирования: почему переопределения только `add` недостаточно?
Если оставить метод `addAll` непереопределенным, пакетное добавление занятий выполнится в обход механизма аудита: элементы запишутся в память, но события журнала не сгенерируются

### Собственные тесты
Проект протестирован как локальными Unit-тестами, так и автоматическим интеграционным скриптом

1. Оригинальный скрипт автоматической проверки `tools/verify.py` был дополнен кастомными граничными файлами, которые генерируются во временной папке:
   * **edge.errors.txt** — содержит строки со всеми видами дефектов (лишние пробелы, скрытая табуляция \t, прочерки вместо аудиторий и дубликаты учителей). Проверено, что программа находит ровно 6 ошибок, выдает правильные сообщения и возвращает код 1.
   * **edge.clean.txt** — содержит корректные строки. Проверено, что команды period и type правильно фильтруют данные, форматируют вывод с разделителями | и выводят верные итоги


2. Unit-тесты
Написаны четыре файла тестов для проверки всех компонентов по отдельности (находятся в `/app/src/test/kotlin/schedule`):
   * ModelTest.kt (проверка доменной модели): проверены ограничения конструкторов и метода copy() на пустые темы, невалидные года (0 и 10000), нехватку или дублирование преподавателей, а также управляющие символы. Отдельно протестирована защита списков от изменений извне
   * ParserTest.kt (проверка парсера): проверен разбор всех типов занятий, реакция на неверное количество полей, отсутствие разделителей |, некорректные даты, а также строгое соблюдение приоритетов ошибок по ТЗ
   * AuditTest.kt (проверка реестра): проверено, что одиночное (add) и пакетное (addAll) добавления корректно обновляют статистику и создают правильное количество событий в журнале (включая пустые пакеты), а метод all() возвращает изолированный неизменяемый снимок
   * RescheduleTest.kt (проверка операции переноса занятия): протестировано успешное создание новой сессии на измененную дату с сохранением всех исходных доменных свойств

## Сообщения об ошибках валидации 

Любые дефекты и нарушения формата во входных файлах обрабатываются как данные с помощью sealed-иерархии `ParseError`
На основе этой структуры метод расширения `logMessage()` формирует понятные текстовые сообщения

### Список сообщений об ошибках приложения

#### Базовые ошибки формата (из ТЗ):
* **Неверный разделитель:** `invalid field separator`
* **Неверное количество полей:** `got N fields, expected 5` (где `N` — реальное число полей)
* **Пустое обязательное поле:** `empty required field "ИМЯ_ПОЛЯ"`
* **Неверный формат или значение даты:** `invalid date "ЗНАЧЕНИЕ"`
* **Неизвестный тип занятия:** `unknown session type "ТИП"`
* **Нехватка преподавателей у сдачи:** `type "EXAM" requires at least 2 teachers, got N`

#### Кастомные сообщения об ошибках домена:
* **Управляющие символы:** `$fieldName field contains control characters` (где `$fieldName` — первое дефектное поле: `topic`, `location` или `teachers`)
* **Внешние пробельные символы:** `$fieldName field has trailing or leading whitespaces` (проверяется внешние границы сырых полей)
* **Неверные поля у отмены:** `cancelled session $fieldNamfields must be "-"` (подставляет имя первого нарушенного поля: `location` или `teachers`))
* **Прочерк вместо аудитории:** `active session location cannot be "-"`
* **Недопустимое имя преподавателя:** `invalid teacher name`  (срабатывает, если элемент внутри списка пуст/состоит из пробелов, имеет внешние пробелы или равен `-`)
* **Повторы в списке преподавателей:** `teachers list contains duplicates`
* **Непредвиденная ошибка домена:** Выводится экранированный текст ошибки из `IllegalArgumentException` (добавлена на всякий случай, если вдруг парсер не словит все доменные ошибки)

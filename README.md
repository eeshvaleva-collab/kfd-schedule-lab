## Структура проекта и назначение файлов

* **`Session.kt`** - ядро модели данных и правила валидации
* **`Parser.kt`** - построчный парсер с валидацией
* **`ParseError.kt`** - иерархия причин отказов и форматтер вывода
* **`Repository.kt`** - слой хранения данных и логирования
* **`Commands.kt`** — реализация логики верхнеуровневых команд (`runPeriod`, `runType`, `runErrors`). Запускает потоковую обработку файлов, фильтрацию занятий и выводит итоговую статистику в консоль

## Сборка:

### Выполните компиляцию, прогон Unit-тестов и создание нативных скриптов запуска:

**Windows PowerShell:**
```powershell
.\gradlew.bat build :app:installDist
```

**Linux / macOS:**
```bash
bash ./gradlew build :app:installDist
```
### После сборки исполняемые скрипты находятся в `app/build/install/schedule/bin/`.
### Примеры команд:

* **Выборка занятий за период (`period`):**
  ```bash
  ./app/build/install/schedule/bin/schedule period --file samples/clean.txt --from 2026-09-28 --to 2027-05-13
  ```
* **Фильтрация по типу занятия (`type`):**
  ```bash
  ./app/build/install/schedule/bin/schedule type --file samples/dirty.txt --type EXAM
  ```
* **Вывод агрегированного списка ошибок (`errors`):**
  ```bash
  ./app/build/install/schedule/bin/schedule errors --file samples/dirty.txt
  ```

### Генерация большого файла и запуск всех тестов из скрипта (включая мои кастомные)
```bash
python tools/generate_samples.py --huge
python tools/verify.py --huge --custom
```

## Обоснование архитектурных решений:
### 1. Выбор между `class` и `data class` для доменной модели
Для реализации конечных типов занятий (`Lecture`, `Practice`, `Exam`, "Cancelled") были осознанно выбраны **`data class`**.

**Обоснование:**
Использование `data class` позволяет избежать написания огромного количества шаблонного кода и гарантирует автоматическую генерацию методов `equals()` и `hashCode()`

**Защита инвариантов при копировании (`copy()`):**
Поскольку автоматически сгенерированный метод `copy()` работает исключительно со свойствами из первичного конструктора, существовал риск обойти проверки бизнес-логики. 
В данном проекте эта уязвимость закрыта: все проверки инвариантов (ограничения на диапазон дат, запрет управляющих символов, валидация внешних пробелов) размещены внутри блоков инициализации `init` каждого класса.

Так как блок `init` гарантированно выполняется при создании экземпляра класса (включая скрытый вызов конструктора внутри автоматически сгенерированного метода `copy()`), модель физически невозможно перевести в невалидное состояние:

---
### 2. Защита коллекций от внешних изменений
Модель защищает коллекции преподавателей как на этапе создания, так и при последующем чтении свойств:

1. **Защита от изменения исходного списка:** Первичный конструктор принимает сырой список в приватное свойство `private val teachersRaw: List<String>`. 
Публичное свойство `override val teachers` инициализируется в теле класса через глубокое копирование методом **`java.util.List.copyOf(teachersRaw)`**.
2. **Защита выданного списка:** Свойство `teachers` предоставляет иммутабельный на уровне JVM список. Любая попытка явного приведения типа к `MutableList` с последующим изменением (`(lecture.teachers as MutableList).clear()`) приведет к немедленной ошибке `UnsupportedOperationException` во время выполнения.

### 3. Поведение делегирования: почему переопределения только `add` недостаточно?
Переопределения `add(session)` недостаточно для корректного учета пакетных добавлений через `addAll(sessions)`:
При вызове непереопределенного метода `addAll` на обертке, компилятор Kotlin перенаправляет выполнение напрямую в объект-делегат (`delegate.addAll`). На уровне байт-кода JVM вызов `this.add()` внутри делегата жестко инкапсулирован внутри контекста самого внутреннего реестра. Внутренние вызовы физически не могут вернуться во внешнюю обертку `AuditedSessionRepository`.

В результате, если оставить метод `addAll` непереопределенным, пакетное добавление занятий выполнится в обход механизма аудита: элементы запишутся в память, но события журнала не сгенерируются

### Собственные тесты
Проект протестирован как локальными Unit-тестами, так и автоматическим интеграционным скриптом

1. Оригинальный скрипт автоматической проверки `tools/verify.py` был дополнен кастомными граничными файлами, которые генерируются во временной папке:
   * **edge.errors.txt** — содержит строки со всеми видами дефектов (лишние пробелы, скрытая табуляция \t, прочерки вместо аудиторий и дубликаты учителей). Проверено, что программа находит ровно 6 ошибок, выдает правильные сообщения и возвращает код 1.
   * **edge.clean.txt** — содержит корректные строки. Проверено, что команды period и type правильно фильтруют данные, форматируют вывод с разделителями | и выводят верные итоги


2. Unit-тесты
Написаны три файла тестов для проверки всех компонентов по отдельности (находятся в `/app/src/test/kotlin/schedule`):
   * SessionModelTest.kt (проверка доменной модели): проверены ограничения конструкторов и метода copy() на пустые темы, невалидные года (0 и 10000), нехватку или дублирование преподавателей, а также управляющие символы. Отдельно протестирована защита списков от изменений извне
   * ParserValidationTest.kt (проверка парсера): проверен разбор всех типов занятий, реакция на неверное количество полей, отсутствие разделителей |, некорректные даты, а также строгое соблюдение приоритетов ошибок по ТЗ
   * AuditedRepositoryTest.kt (проверка реестра): проверено, что одиночное (add) и пакетное (addAll) добавления корректно обновляют статистику и создают правильное количество событий в журнале (включая пустые пакеты), а метод all() возвращает изолированный неизменяемый снимок

## Сообщения об ошибках валидации 

Любые дефекты и нарушения формата во входных файлах обрабатываются как данные с помощью sealed-иерархии `ParseError`. На основе этой структуры метод расширения `logMessage()` формирует понятные текстовые сообщения на английском языке.

### Список сообщений об ошибках приложения

#### Базовые ошибки формата (из ТЗ):
* **Неверный разделитель:** `invalid field separator`
* **Неверное количество полей:** `got N fields, expected 5` (где `N` — реальное число полей)
* **Пустое обязательное поле:** `empty required field "ИМЯ_ПОЛЯ"`
* **Неверный формат или значение даты:** `invalid date "ЗНАЧЕНИЕ"`
* **Неизвестный тип занятия:** `unknown session type "ТИП"`
* **Нехватка преподавателей у сдачи:** `type "EXAM" requires at least 2 teachers, got N`

#### Кастомные сообщения об ошибках домена:
* **Управляющие символы:** `value contains control characters`
* **Внешние пробельные символы:** `value has trailing or leading whitespaces`
* **Неверные поля у отмены:** `cancelled session location and teachers fields must be "-"`
* **Прочерк вместо аудитории:** `active session location cannot be "-"`
* **Недопустимое имя преподавателя:** `invalid teacher name`
* **Повторы в списке преподавателей:** `teachers list contains duplicates`
* **Нехватка преподавателей для других типов занятий:** `type requires at least 2 teachers, got N`
* **Непредвиденная ошибка домена:** Выводится экранированный текст ошибки из `IllegalArgumentException`.
